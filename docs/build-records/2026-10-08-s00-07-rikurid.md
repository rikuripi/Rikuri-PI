Cause (code reading): `Kernel::state` runs inside `Store::read`, which holds the store's connection `Mutex`, and calls `Store::schema_version`, which locks the same non-reentrant `Mutex`. The bug predates today's storage changes (`schema_version` locked the connection on 2026-10-05 too); the command was never run.

Same class as the storage owner-only defect fixed in PR #18.

## 3. Debug

- [ ] Defect A reproduced by a red test (in-process and through the socket, with a timeout so the suite fails instead of hanging).
- [x] Root-cause class (A): **a lock re-entered through the store's own API inside its transaction closure.** `Store` methods that lock the connection (`read`, `write`, `schema_version`) must never be called from inside `read`/`write`; with a non-reentrant `Mutex` the result is a silent hang, which Law 1 forbids. Sibling sweep: every `self.store.*` call inside a `read`/`write` closure in `rikurid` (to do with the fix), and a tripwire in `rikuri-storage` so a re-entrant call returns an error instead of deadlocking.
- [x] Root-cause class (B): a guarantee stated more broadly than its mechanism (owner-only only when the directory is created), the class fixed in storage in PR #18. Sibling sweep: every file or directory `rikurid` creates (socket, socket directory; the database goes through `Store::open`).
