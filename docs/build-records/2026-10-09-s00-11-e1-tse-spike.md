## 1. Plan

- [x] One-sentence statement: decide, with evidence, whether kernel transactions need anything beyond one SQLite transaction (plus what it already does) to satisfy Transactional State Evolution, and record the outcome.
- [x] Owner request 2026-10-09: "Start on E1".
- [x] The claim under test (Stage Plan, experiment register): "Find the simplest implementation satisfying Transactional State Evolution and last-known-good recovery. Compare versioned SQLite transaction with an explicit candidate/promotion design at Stage 00 kernel crash points … If versioned SQLite transactions satisfy the same invariant and crash tests, omit redundant ceremony; if neither passes, Stage 00 remains open." Full matrix (all eight points) at Stage 05.
- [x] The invariant (Architecture §43): preserve/read old authoritative state → validate inputs → transform complete candidate → validate candidate → durably write → read back and verify integrity and semantics → atomically promote → only then retire/archive old state; on any pre-commit failure the last known-good state stays authoritative and the operation is retryable; test each crash point and restoration.
- [x] Current behaviour characterized (before the spike):
  - one IMMEDIATE transaction per consequential command (`Kernel::consequential`): idempotency check, plan (typed objects, version checks), repository writes with read-back of every row, event appends, idempotency record, commit; WAL, `synchronous=FULL`, `quick_check` at open (ADR 0002);
  - W1 (T00.06–T00.08, T00.12, placement): a crash before the commit leaves the last known-good state, after it the whole change, and the retry gives one effect;
  - the read-back has no test that makes it differ (nothing proves it bites);
  - candidate validation beyond typed construction and read-back happens only after commit: the consistency replay at open and on `system.health` quarantines writes, by which time a bad candidate is already authoritative;
  - `synchronous=FULL`'s cost is not measured (ADR 0002 follow-up), and power loss (as opposed to a killed process) is not tested.
- [x] **I will know E1 is answered when:**
  - each TSE step has a named mechanism and a test that fails without it, or a recorded reason it is N/A or Not yet proven;
  - the read-back is shown to bite (a row that differs on read-back rolls the transaction back and leaves the last known-good state);
  - a planted kernel defect that would promote an inconsistent candidate is measured both ways: with the current post-commit replay (caught after promotion, writes quarantined) and with a candidate check scoped to the command's own objects before the commit (never promoted), with its cost;
  - a candidate/promotion prototype runs the same Stage 00 crash points and is compared on outcomes, commits and fsyncs per command, latency and code;
  - `synchronous=FULL` versus `NORMAL` latency is measured on the reference machine;
  - the outcome (keep, simplify or drop, and any change to the kernel) is written as an ADR for the owner, and the experiment register's Outcome cell is filled once the owner accepts.
- [x] Architecture impact: [ADR 0005](../architecture/adr/0005-e1-transactional-state-evolution-for-kernel-transactions.md), accepted 2026-10-09, clarified 2026-10-10: kernel transactions stay one SQLite transaction, explicit candidate/promotion is dropped for them, and a candidate check runs before the commit.
