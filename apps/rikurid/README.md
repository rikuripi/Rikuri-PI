# rikurid — Module Contract

Template C, [Engineering Templates v1.1](../../doc/Rikuri_Pi_Engineering_Templates_v1.1.md#template-c--module-contract). Stage Plan item S00.07.

## Purpose

The trusted Rikuri daemon: the only process that changes canonical state (Architecture §6.2). It opens the canonical store under a Rikuri home directory, serves the versioned envelope of `rikuri-api` over a local socket and in-process, and runs every command through one kernel (`Kernel::handle`), so both adapters share all kernel code (T00.09).

## Owns

- The kernel: the Stage 00 commands (`system.init`, `system.health`, `task.create`, `task.start`, `task.step`, `task.complete`, `state.show`, `ledger.tail`) and their validation. A client idempotency key on a command that takes none (`system.init`, which has its own built-in key, and the read-only commands) is refused, not ignored.
- The one-transaction path for every consequential command (Architecture §8): idempotency check → state change → event append → idempotency record → candidate check → commit. A retry with the same key returns the stored response and changes nothing; the same key with a changed request is `idempotency_conflict`. The candidate check is Transactional State Evolution's "validate candidate" step (Architecture §43; ADR 0005 and its 2026-10-10 clarification, E1). It validates what the command wrote and appended (`candidate::check_writes`), read from the transaction itself: the store's write list `Tx::written`, and the ledger's events after its newest sequence number when the command began (`rikuri_ledger::after`), so a write or append that the plan does not list is checked too. Every event appended is about a task (and, except `task.created`, a run) the command wrote, and no two carry the same type and idempotency key; every existing task or run written is named by one of those events, and every new one has exactly its creation or start event; each change moves by what its events say (a new task or run starts empty, step and run counts move by the step and start events, a completion records what its completion and verification events say, a completed run does not change); a task that leaves its current run ends that run in the same command; each written task holds the task ↔ run pointer invariants after the change, and a written run that is still running has no completion link, outcome or verification; and each written task's counts match the ledger, counted through the ledger's `(task_id, event_type)` index without reading event rows. On top of these general rules, each task command has an exact spec (`src/candidate/spec.rs`; owner decision 2026-10-10 after verifier round 3): the event types it appends, in order and how many; each event by the owner, succeeded, under the command's key, with exactly the command's references and metadata; exactly the task and run it writes; and every field of them equal to the before-state with only that command's changes applied (the frame rule), so a title, privacy class, deletion unit, project, attempt, status or last run that no rule names cannot change unnoticed. A command with no spec is refused. A step or completion must name the task's own running current run, and a new task's deletion unit must be its own (`rikuri_storage::deletion_unit_size`, an index lookup). With idempotency enforced, the record the command wrote must be its own, under that command and request, pointing at its first event (`candidate::check_recorded`; without it a retry would run again, and under another command a retry would be refused). The records written are read from the ledger by rowid from a mark taken when the command began: with idempotency enforced exactly one, under the command's key, storing exactly the response it returns, so a retry answers as the first call did; with it off, none (`candidate::check_record_written`). Both are chosen by the idempotency mode, never by the kernel's own note that it wrote a record. The answer the command returns (and records for every retry) must name exactly what it wrote: its task, run, version and events, and the steps, outcome and verification it reports; `system.init`'s its owner, Inbox and event (`candidate::check_answer`). Every event appended carries the ledger's current schema version (`rikuri_ledger::EVENT_SCHEMA`). The check's cost grows with the written task's history through the index-only count: roughly 0.1 to 0.2 ms per 1,000 events on the task (from within noise to +0.7 ms per command after 1,000 steps, +0.5 to +1.0 ms after 6,000, +1.9 ms after 20,000), against +2.4 ms at 6,000 without the index (E1 record). A run's step count is checked as a change, not against the ledger's total for that run (owner decision 2026-10-10). `system.init`, which writes the owner and project into an empty store, gets the full replay instead, and its own spec (`candidate::check_init`: exactly one new owner and one new Inbox project with default trust and intent, so no project starts trusted for execution, and its `system.initialized` event by the owner); every other command goes through the write-set rules, which refuse any object kind or event type they do not cover, so a new command fails closed until it has rules of its own. A disagreement refuses the command before promotion (`internal`, "candidate refused before promotion …"), and the store counts it as a failed write. Drift in objects the command did not write is the full replay's to find, at open and on `system.health`. One SQLite transaction is the whole of TSE for a kernel command; explicit candidate/promotion is for multi-store work (ADR 0005).
- Read-only quarantine (owner decision 2026-10-08): when the ledger-consistency check fails, because current state and history disagree or because the check could not run, at open or on any later check, the daemon keeps serving reads and `system.health` (with a Critical `writes` component and a `quarantined` field naming the problem, so health is never green while writes are refused, even after the cause has cleared) and refuses every write with `quarantined` until the owner repairs the store and restarts the daemon. A retry of a request already committed still gets its stored response (owner decision 2026-10-08: a replay only reads). The quarantine lasts for the daemon's lifetime.
- The Stage 00 entities in the object registry: `Owner`, `Project` (untrusted for execution), `Task` (its title is owner content, with a privacy class and its own deletion unit, never copied into an event), `Run` (completion and verification recorded separately). `state.show` lists at most 1000 tasks and sets `tasks_truncated` when there are more.
- Crash points 1, 2, 3 and 6 (Test Strategy §5): before the transaction, after the state write, after commit, before the response. Production uses `NoCrash`; `crash-injection` builds can hang at a point for a SIGKILL harness (its stop marker prints the command's `Progress`), and in-process tests use `rikuri-testkit`'s `CrashInjector`. The vocabulary (`CrashPoint`, `Crashed`, `Progress`, `CrashHook`) lives in `rikuri-domain` and is re-exported here. The kernel tells every hook what the command has done so far (`Progress`: transaction open, state written, events appended, idempotency recorded, committed), read from facts when the point is reached (the store's `in_transaction`, SQLite's change count, the ledger's newest event, the idempotency write), so tests pin where each point sits. `RIKURI_CRASH_AT` must name a known point and a command that writes (only those reach a crash point).
- Health on evidence (Architecture §27.8, §53.7): components `build`, `store` and `ledger_consistency`; a component that has never succeeded is not Healthy. The store is judged on reads and writes separately, so a successful read (including health's own consistency replay) cannot hide a failing write, and a refused request is not a store failure. The ledger-consistency check replays history against current state at open and on `system.health`, in both directions: each task's and run's links into the ledger, and each ledger event about a task or run back to state (an unlinked completion, an outcome or verification that differs from the ledger, a step count that differs), state's own task ↔ run pointers (a running task has a current run that is a running run of it, every running run is its task's current run, a task's last run exists and is its own), and the owner and project against `system.initialized`. It is also the crash matrix's no-duplicate-effect check (W1).
- The local socket server: one request line per connection, one response line, `REQUEST_TIMEOUT` per read, `MAX_REQUEST_BYTES`. Every request, including one refused before it parses, is logged by command and outcome only, never by parameters; the command name is escaped and bounded so it cannot forge a log line. A stale socket left by a dead daemon is replaced; anything else at the socket path (a regular file, a directory, a symlink) is refused and never deleted.
- The home directory layout: `state/rikuri.db` (via `rikuri-storage`, whose writer lock makes it one daemon per home) and `run/rikurid.sock`. Home defaults to `$RIKURI_HOME`, then `~/.local/share/rikuri`.

## Must not own

- Storage mechanics, migrations or the ledger's tables (`rikuri-storage`, `rikuri-ledger`).
- The envelope's shape or error vocabulary (`rikuri-api`).
- Models, tools, network access, policy decisions beyond Stage 00 commands: later stages.

## Trust level / boundary

Trusted. Every request is untrusted input: envelope version, request ID length, command name, parameters and idempotency keys are validated, unknown fields are refused, and error text quoting the request is bounded. The socket and its directory are owner-only: an existing socket directory that group or others can access is refused, because the socket briefly has the umask's mode between `bind` and its `chmod 0600`.

## Canonical data touched

`objects` (owner, project, tasks, runs) and, through the ledger, `events` and `idempotency`.

## Public contracts / interfaces

Binary `rikurid [--home DIR] [--socket PATH]` (`--help` prints the usage and exits 0). Library: `Kernel::{open, handle, check_consistency, quarantined, store}`, `KernelConfig`, `KernelError`, `Idempotency`; `kernel::database_path`; `server::{bind, serve, socket_path, REQUEST_TIMEOUT, MAX_SOCKET_PATH_BYTES}`; `crash::{NoCrash, HangAtPoint}`, and the crash vocabulary `crash::{CrashPoint, CrashHook, Progress, Crashed}` re-exported from `rikuri_domain::crash`; `health::{ComponentHealth, HealthState, report, ConsistencyReport}`; `entities`.

## Allowed dependencies

`rikuri-api`, `rikuri-domain`, `rikuri-ledger`, `rikuri-storage`, `serde`, `serde_json`, `thiserror`. Test-only: `proptest`, `tempfile`, `rikuri-testkit`.

## Forbidden dependencies

Any network, async runtime, provider or model crate in Stage 00.

## Failure and degraded behavior

A command fails with a typed `ApiError`; storage failures map to `storage_failure`. A crash at any point leaves either no change or the whole change, and the retry with the same key returns the original outcome. A candidate whose writes or events break a general rule or its command's spec is refused with `internal` ("candidate refused before promotion …") while the last known-good state stays authoritative, and counts as a failed write in the store's health; nothing is quarantined for it. Disagreeing state and history found by the full replay, at open or on `system.health`, quarantine writes (above). A second daemon on the same home fails to open (`rikuri-storage`'s writer lock). A build with `crash-injection` reports itself Degraded, and with idempotency off, Critical. A production build that sees the test variables warns that it ignores them.

## Health / last-success signal

`system.health` returns the worst component state, then each component, and `quarantined` when writes are refused:

```text
state / last_attempt / last_success / last_error / consecutive_failures / work_completed:
  build               — Healthy only in the production configuration
  store               — from rikuri-storage's StoreHealth: Degraded after 1–2 failed reads or
                        writes in a row, Critical after 3; reads and writes judged separately.
                        Covers the whole write path: an internal kernel fault inside a write
                        transaction counts here too, and the detail names the cause
  ledger_consistency  — last replay of history against current state
  writes              — only while quarantined: Critical, naming why writes are refused
```

## Threat / control links

- Threat: a retried or crash-replayed command applies twice. Control: one transaction with the idempotency record. Tests: `replay_and_conflict`; T00.06 `tests/t00_06_no_duplicate_effects.rs`; T00.07 and T00.08 `tests/crash_matrix.rs`.
- Threat: the daemon keeps writing on top of state it cannot trust. Control: read-only quarantine, sticky, with health Critical throughout. Tests: `disagreeing_state_quarantines_writes`, `quarantine_keeps_health_critical_after_the_cause_clears`, `a_quarantined_daemon_still_replays_committed_requests`.
- Threat: owner content leaks into logs or the audit trail. Control: requests logged by command and outcome only; task titles never copied into events.
- Threat: health reports green while writes fail, or on liveness alone. Control: reads and writes judged separately; never-succeeded is not Healthy; refusals are not failures. Tests: `store_health_reports_failed_writes`, `refused_requests_do_not_mark_the_store_failed`, `a_store_without_success_is_not_healthy`.
- Threat: starting the daemon destroys a file at a mistyped socket path. Control: only a socket is ever replaced. Test: `bind_never_deletes_a_file_that_is_not_a_socket`.
- Threat: two daemons write one home. Control: the store's writer lock. Test: `one_kernel_per_home`.

## Known limitations / explicit debt

- Fixed 2026-10-08, tests-first ([S00.07 record](../../docs/build-records/2026-10-08-s00-07-rikurid.md)): `state.show` deadlocked the daemon; an existing socket directory was not checked; health showed the store healthy while writes failed; `bind` deleted any non-socket file at the socket path; and the smaller items listed in that record.
- One connection at a time with a per-read timeout: a slow or non-reading client can stall the daemon for others. Acceptable while the socket is owner-only (ADR 0004); must change before any caller other than the owner can reach a socket (for example the Pi harness's mounted socket, ADR 0000 September 28 decision 3).
- Fixed 2026-10-08, tests-first ([crash matrix record](../../docs/build-records/2026-10-08-stage-00-crash-matrix.md)): the consistency replay followed only the links state pointed at, so a completion that state forgot or an outcome that differed from the ledger passed; then (verifier round 1) task ↔ run pointers and the owner were not compared at all. Also (verifier round 2): an unarmed `crash-injection` build reported "production configuration"; it is now Degraded, and the gate builds it in `target/crash-injection` so it never replaces `target/debug/rikurid`.
- The crash matrix covers Stage 00's points 1, 2, 3 and 6. Tool, budget and backup points (4, 5, 7, 8) arrive with those systems, and all eight rerun at release (Stage Plan T00.07). Points 3 and 6 coincide today: nothing runs between the commit and the response inside the kernel, so their cells are the same until a response path sits between them. Each point's position is pinned too: the hook receives `Progress` read from facts when the point is reached (the store's `in_transaction`, SQLite's change count, the ledger's newest event, the idempotency write), and the placement tests fail if a point moves ([W1 placement record](../../docs/build-records/2026-10-09-w1-crash-point-placement.md)).
- The pre-commit candidate check covers what a command writes. Drift already in state that the command does not write (an earlier run's outcome, another task) is found by the full replay at open and on `system.health`, after which writes are quarantined; until then commands on other objects keep committing (owner decision 2026-10-10, ADR 0005 clarification).
- The candidate check sees the writes the repository lists (`Tx::written`) and every event and idempotency record added after the marks taken when the command began (read from the ledger, so an append outside the plan is covered). It runs once, after the plan, the events and the record: a replay answered from a stored record returns before it, and nothing is written after it today; a write placed in either spot would not be checked before the commit (verifier round 7, M1; owned debt in the E1 record). The kernel writes objects only through `SqliteRepository` (no SQL on `objects` in `src/`); an object write made any other way would not be checked before the commit. The replay afterwards sees only what the ledger can contradict (counts, links, pointers, outcomes); a change to a title, privacy class, deletion unit or project made that way would go unnoticed (verifier round 3, V10).
- `src/candidate.rs` (1754 lines: 572 of code, 1182 of inline unit tests, 33 tests) and `src/candidate/spec.rs` (1719 lines: 535 of code, 1184 of tests, 17 tests) are both over the 1200 that needs a reason. Each file's code is well under the 800-line review mark; the length is tests, kept inline as every unit-test module in the workspace is. Moving each file's tests to their own file is a reasonable later tidy-up.
- Unix only (local socket); Windows arrives with Windows support (product Stage 9).
