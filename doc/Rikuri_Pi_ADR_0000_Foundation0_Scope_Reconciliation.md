# ADR 0000 — Foundation-0 scope and acceptance reconciliation

**Date:** September 24, 2026  
**Status:** Adopted planning baseline; implementation claims remain unproven until their gates pass  
**Applies to:** PRD v1.1, Architecture v1.6, Engineering Standard v1.1, Foundation-0 Re-baselined Stage Plan v2.0  
**Owner:** Rikuri Pi product owner

## Context

The PRD describes the full product and a broader Foundation Release. The architecture and earlier 90-Day Build Plan used F1–F10 for a 13-week slice. The owner has chosen a six-stage Foundation-0 plan with time to test and observe real results. Treating every product-level P0 or the broader Foundation Release checklist as a June 2027 promise would make the plan inconsistent and push technical risks late into the build.

## Decision

The **Foundation-0 Re-baselined Stage Plan v2.0** is the live gate schedule. Six stages run sequentially from October 2026 toward a June 2027 planning target; reserve four to eight weeks of contingency into July–August. Dates are estimates. A required gate stays red until its repeatable demonstration and linked technical evidence pass. The PRD retains the larger product vision and product-level P0 priority; the broader Foundation Release is later than Foundation-0.

| Claim or dependency | Foundation-0 commitment | Later product commitment / boundary |
| --- | --- | --- |
| W1 continuity | Kernel crash points at Stage 00; full eight real cross-component crash points at final release | Further platform and multi-node fault modes get their own gates |
| F2 import | Real ChatGPT and Markdown/Obsidian import with provenance and idempotency in Stage 01 | Claude and read-only Git/project manifest importers early Stage 1 |

Each stage ends with an owner-runnable demonstration and a plain-language **Pass / Fail / Not yet proven** receipt. Tests, failure drills, and appropriately independent adversarial review back claims the owner cannot verify by reading code. An agent’s completion claim is insufficient. The public-exposure release gate in the Engineering Standard remains separate and includes its human external security audit.

## Early risk decisions

1. Stage 00 probes bubblewrap namespace creation on the pinned Ubuntu image under its default AppArmor settings. If unavailable, choose and test a safe alternative through an ADR; do not disable system-wide restrictions to make a test pass.
2. E1–E6 are time-boxed experiments. E3 cannot turn a weaker forget/restore promise into a green F6. E4 cannot green-light an always-abstain knowledge compiler. E5 cannot report network denial from configuration alone.
3. Only one tested OpenAI-compatible cloud access path is in the first slice, using synthetic non-sensitive fixtures at Stage 02. Provider gateways need capability-specific testing; a shared wire format alone does not certify production behavior.
4. Speculative additions go to the parking lot. A real change to a promise or security boundary requires an ADR, revised PRD and architecture text, current acceptance tests, and updated runbooks in the same change. This record does not freeze documentation against corrections.

## Consequences and open implementation questions

- The earlier 90-Day Build Plan v1.6 is historical, not a parallel gate board. The Master Build Sequence now points to the live plan; future stages are re-estimated from evidence at each gate.
- The exact durable revocation storage and recovery-key protocol, viable Ubuntu envelope backend, and cloud/local handoff state schema are implementation decisions to prove through E3, E5, and Stage 04. Until then their guarantees are requirements, not implemented facts.
- If an experiment fails, keep the dependent gate red and record an ADR-backed redesign or explicit owner decision on any weaker product promise. Do not silently reduce an acceptance test to match elapsed time.
- No actual build or security gate has passed merely because these planning documents agree.

## September 28, 2026 — Option C review follow-ups and Foundation-0 credential scope

**Decision: adopted at the owner's request after an independent review of the Option C change.** The Option C decision above stands. This addendum closes gaps the review found and records one owner scope choice. Earlier text is preserved.

1. **Backend-native approval channels are disabled for Rikuri workers.** OpenShell v0.1.2 lets a sandboxed process submit policy proposals through `http://policy.local`, drafts proposals from denials, and can merge prover-clean proposals automatically when `proposal_approval_mode` is `auto`. That is a second authority path beside Rikuri's grants. Admission requires the mode pinned to manual at gateway scope and checked as part of the effective policy on every launch; the worker's proposal route is blocked, or its proposals reach Rikuri only as untrusted requests rendered by the Trusted Approval Renderer. OpenShell's own approve/reject surface is never used for Rikuri workers. The same rule applies to any later backend with a comparable feature.
2. **Container-engine access is root-equivalent and stays out of Rikuri's processes.** The candidate backend controls a rootful container engine through its socket, and its supervisor uses host networking. The reference installation runs the backend's controller under a dedicated service account or a rootless engine; the accounts that run `rikurid`, Pi, local model servers and tool servers are not in root-equivalent groups such as `docker` or `lxd`. S00.13 records this; the supervisor and engine are part of the trusted computing base, and their reach to host services is tested.
3. **Pi placement and model routing are decided in E2, before Stage 04 design.** Either the Pi process runs inside the admitted envelope, or E2 proves its built-in file/shell tools and extension loading are disabled and it holds no host authority; otherwise E2's kill criterion fires. Pi never holds a provider credential: its model provider is a `rikurid`-owned endpoint that applies context admission, the hard budget reservation and the task's privacy class to every request. Local Only work reaches the local runtime only through that endpoint over a mounted local socket, so the worker's network policy stays empty. If E2 or Stage 04 finds the socket route impossible, a loopback or host-service allowance is a permitted destination: decision 4's N/A no longer holds for it, and its qualification rows return to Stage 03/04.
4. **Foundation-0 workers hold no real credential and have no permitted external destination (owner choice).** Cloud model access stays inside `rikurid`'s provider adapter. Broker qualification (SEC-022) and permitted-destination leakage tests are therefore N/A in Foundation-0 (a loopback or host-service allowance counts as a permitted destination) and become mandatory, with the full Test Strategy §8.2 rows, when a later stage first enables a credential-bearing or network-permitted worker. Stage dates are unchanged. *Cost:* Foundation-0 cannot demonstrate a worker using an account, API key or web destination. *Reversal:* the owner may admit such a path inside Foundation-0 through a later dated addendum, which reinstates those rows as Stage 03 exit requirements and re-estimates Stage 03.
5. **Baseline freeze.** The planning baseline is frozen for Foundation-0 execution from this addendum. New ideas go to [`docs/PARKING_LOT.md`](../docs/PARKING_LOT.md); changes to promises, security boundaries or acceptance still use a dated ADR and matching tests. Stage Gate Records link the live Stage Plan rather than copying it.

No gate closes and no S/T/E identifier changes. See the [Build Record](../docs/build-records/2026-09-28-option-c-review-followups.md) and the [threat model](../docs/security/THREAT_MODEL.md).

## September 28, 2026 — reference installation and requalification tiers

**Decision: adopted at the owner's request.** Earlier text is preserved.

1. **Reference installation.** The owner's current machine is Foundation-0's Ubuntu reference. It runs the newest stable Ubuntu LTS with that release's standard (GA) kernel, never a hardware-enablement (HWE), OEM or mainline kernel: Ubuntu 26.04 LTS with kernel 7.0, upgraded from 24.04 LTS through Ubuntu's supported path before S00.13 (on 2026-09-28 that path was not yet offered; the Stage 00 record holds the status and the owner's options). S00.13 is admission evidence only; the full qualification runs once at Stage 03 on the 7.0 kernel, and afterwards 7.0-series security patches use the tier-1 rerun. The reference moves to the next LTS (expected 28.04) after its first point release, as a planned tier-2 requalification between stages. *Why not HWE:* Ubuntu's HWE and OEM kernels roll to newer series over an LTS's life (on this machine, 24.04's HWE kernel is already 7.0 and its OEM kernel 6.17, against the 6.8 GA kernel), and each roll is a tier-2 full requalification; an interim HWE kernel cannot be kept once its successor ships, because its security updates stop. Moving to an HWE kernel (for example 7.3 via 26.04.2) remains possible as a deliberate owner decision with that recurring cost. The owner chose 7.0 knowing the kernel is shared with the node on this machine; whether the node needs anything newer is the node's own question. The machine also runs the owner's Bitcoin node on a rootful Docker engine; the sandbox controller never uses that engine (review follow-ups, decision 2). Details: the [Stage 00 Stage Gate Record](../docs/stage-gates/foundation0/00-bootstrap-kernel.md).
2. **Two requalification tiers.** The earlier rule that any kernel, image, backend or configuration change requires requalification is refined, not weakened. The rule is defined once, in the [Engineering Standard](Rikuri_Pi_Engineering_Standard_v1.2.md#security-assurance-and-upstream-maintenance): tier 1, an automated regression rerun, applies only to an explicitly listed set of patch-level changes; everything else, including any change not listed as tier 1 and any tier-1 failure, is tier 2, the full qualification. From the moment a running component changes, affected profiles are unavailable until the applicable tier passes, and evidence binds to the running kernel. Without the tiers, every weekly kernel security update would force the full qualification. *Cost:* container engine/runtime updates are tier 2 unless the S03.11 ADR moves them to tier 1 with a written reason and covering check.

No gate closes and no S/T/E identifier changes. See the [Build Record](../docs/build-records/2026-09-28-reference-installation-and-requalification-tiers.md).

## October 8, 2026 — mission charter and platform independence

**Decision: adopted by the owner on October 8, 2026, choosing "fold in and keep the charter"** over three alternatives: folding in without a charter, adopting the draft as a governing addendum above the PRD, or recording it only in the parking lot. Earlier text is preserved.

The owner stated Rikuri's mission: free people from being trapped by any one OS or ecosystem, and expand their horizon and capability, rather than serve as a generic AI orchestration layer for an operating-system company. The supplied "Proposed Addendum A v1.0" (October 7) is kept, corrected, as the [Mission Charter v1.0](Rikuri_Pi_Mission_Charter_v1.0.md). The charter is rationale and a decision test, not a second requirements source or roadmap; the PRD and Architecture govern where they differ. The [review](reviews/2026-10-08-mission-addendum-review.md) records what already agreed, what was new and each correction.

1. **New promises, under the baseline freeze.** PRD principles P32 (capability over automation), P33 (use platforms; belong to none) and P34 (platform claims at their proven level); PRD §29 MISSION-001–006; three post-Foundation §22 measures; [Architecture §26.5](Rikuri_Pi_Architecture_Spec_v1.7.md#265-platform-claim-states-architectures-and-vendor-ai-layers) (four claim states, processor architectures, vendor AI layers, heterogeneous compute); and future acceptance in Test Strategy §20.
2. **Vendor AI layers are adapters, never homes.** OS-integrated model runtimes, NPU frameworks and built-in vendor assistants enter only through the existing runtime/tool admission path and never hold canonical state. Local Only work may use one only while the runtime itself executes inside an admitted network-Denied envelope for that execution, requalified on runtime or OS change; a layer that runs as an OS service with its own network, or can route to its vendor's cloud, is a cloud path. Vendor memory, history or personalization counts as provider retention under SEC-028, and an acting built-in assistant is an opaque native worker that fails closed (SEC-021). Local Only, Secret exclusion and Option C are not weakened.
3. **Inference about the user stays late.** Charter §3.5 (noticing stalled projects and recurring failures) and §6 (adapting to demonstrated competence) are learned behavior: product Stage 10 after Stage 4 evidence and Stage 6 governance, consistent with "instrument early; infer late". Stage 2 keeps only what it already plans: creative-mode advice and teaching (WIDE-006), text contextual questions (WIDE-007; voice Ask and Dictate stay Stage 8) and requested reflection (STUDIO-004); Stage 2 capability reports show only lessons the user saved and outcomes they declared (MISSION-002). A general mode selector goes to the parking lot.
4. **New features go to the parking lot**, not the PRD: ARM64 CI, NPU scheduling and prefill/decode disaggregation, vendor-runtime adapters, and creative production app adapters. ARM64 on Linux and Windows is a declared target (MISSION-005) without a stage.

5. **Decision test as a process step.** MISSION-001 adds the decision-test answer to the parking lot's "Leaving the lot" procedure and to post-Foundation re-estimations. Its first use falls at the parking-lot review held with S05.10; it is outside S05.10's acceptance and changes no gate. Likewise, MISSION-003's four availability states apply to new or revised documentation written during Foundation-0, such as Stage 05 release notes, as a writing rule rather than a gate.

*Cost:* one more document to keep consistent; a decision-test answer for each entry leaving the parking lot, starting during Foundation-0 at the S05.10 review; and availability claims in new or revised documentation written in the four states. *Reversal:* a later dated addendum may retire the charter or any MISSION row; the PRD's earlier neutrality principles stand on their own.

Foundation-0 stages 00–05, S/T/E identifiers, gate states, the platform order and dates are unchanged. No runtime evidence is claimed. See the [Build Record](../docs/build-records/2026-10-08-mission-charter.md).
